# Converter projects - shared conventions

Every `<Format>_to_AdHoc` folder here turns a machine-readable schema of some protocol into AdHoc
protocol-description `.cs` files. The reference implementation is the MAVLink-to-AdHoc converter (MAVLink XML → AdHoc).

**Every project is fully isolated.** It carries its own copy of the emitter helpers
(`src/org/unirail/adhoc/AdHocWriter.java`, `Json.java`), its own `validate.sh`, its own samples, README and
scripts. No project references files of another project or of this folder; each one builds and runs on its own.

## This project is the C# member

Everything below holds here, with one difference of form: the converter is written in C# (.NET 10) on top of the
Microsoft.OpenApi reader, not in Java. So in this project

- the converter is `src/OpenAPI2AdHoc.cs`, built by `OpenAPI2AdHoc.csproj` (`dotnet build … -o out`);
- the local copy of the naming rules is `src/adhoc/AdHocNames.cs` (the agent's keyword list and `brush`), and the
  emitter helpers live in the converter itself;
- the two NuGet packages of the reader are its only dependencies, restored by the build.

The CLI contract, the shape of a generated file, the rules of a generated description and the mandatory
validation are the same. One rule is stricter here, because OpenAPI names repeat far more than the names of the
other formats: when two names conflict, the **deeper** one changes, and it changes by raising the case of its
letters one after another until the conflict is gone; a number is appended only when case cannot tell the names
apart.

## Layout of one project

```
<Format>_to_AdHoc/
  README.md                    purpose; LINKS to the format specification and to the sample sources; mapping
                               table; build / fetch / run / validate commands; validation result; limitations
  src/org/unirail/<Format>2AdHoc.java   the converter (Java 17, javax.xml + the local Json.java, no other deps)
  src/org/unirail/adhoc/AdHocWriter.java, Json.java   local copy of the emitter helpers (edit freely, it is yours)
  src/org/unirail/adhoc/Originals.java   reads sources.txt: the original page of an input, for the header
  fetch-samples.sh             downloads real upstream schema files into samples/ (curl or git) and lists
                               their original pages in samples/sources.txt
  samples/                     the fetched inputs
  build.sh                     javac (src → out) and a run over samples/ into AdHoc/
  validate.sh                  runs AdHocAgent in parse-only mode over AdHoc/*.cs
  AdHoc/                       generated descriptors, kept for review
```

Build line (run from the project folder):

```bash
javac -encoding UTF-8 --release 17 -d out src/org/unirail/adhoc/*.java src/org/unirail/*.java
java -Dfile.encoding=UTF-8 -cp out org.unirail.<Format>2AdHoc samples AdHoc
```

CLI contract: `<input file or folder> [output folder]`, output defaults to `<cwd>/AdHoc`, one `.cs` per top-level
input (or one per logical bundle when the source format is one schema spread over many files, e.g. a DSDL
namespace tree or a ROS package). Exit code 2 when any input failed; never swallow exceptions silently.

## Shape of a generated file

```csharp
// Generated by <Format>2AdHoc … / Sources: …            ← AdHocWriter.fileHeader (comments attach to nothing)
using System;
using org.unirail.Meta;

namespace org.<format> {
    /** <see cref='Pack' id='N'/> … */                     ← AdHocWriter.dashboard, directly above the interface
    public interface <Project> {
        …packs, enums, constants containers, typedefs…
        struct <HostA> : Host { }   struct <HostB> : Host { }    ← AdHocWriter.host (all six language markers)
        interface <Connection> : Connects<HostA, HostB> { … }    ← states / RPC methods
        …custom attribute declarations…                          ← AdHocWriter.attribute, INSIDE the interface
    }
}
```

The header links the originals. `fetch-samples.sh` writes `sources.txt` next to what it downloads, one line
per file: `<path relative to that folder> <page of the original>`. The page is the file in its repository
(`https://github.com/<owner>/<repo>/blob/<ref>/<path>`), not its raw text; a path that ends with `/` stands for
every file under that folder (a git clone), and the rest of the path is added to the page. The converter looks
every input up through `Originals` (`src/org/unirail/adhoc/Originals.java`, `src/Originals.cs` in the C#
projects; the nearest `sources.txt` above the input decides) and writes the pages under the `// Sources:` line,
one per line. A description made from a whole folder tree links the folders, not every file. An input with no
such list gets no link, so the user's own files convert as before.

## Rules of a generated description

- **Every class must be inside the project interface.**
- **Names**: use `AdHocWriter.ident()` / `brush()` for every identifier (keywords of C#, C++, Java, TS, Rust, Go are
  renamed the way the agent does it; names must not start/end with `_`). A pack cannot contain a field or nested
  type with its own name. Keep names unique within their scope (`AdHocWriter.unique`).
- **Docs**: only through `AdHocWriter.doc()` (XML-escaped `/** */`). Never start a doc line with `*` or `//`.
- **Enums** need at least two members; emit smaller ones as a `struct` constants container. Use `[Flags]` only when
  the source says the enum is a bit set. Widen to `: long` / `: ulong` when values need it.
- **Custom attributes** (`[Units("m")]`, `[Default(…)]`, …) are the way to carry source metadata; declare them with
  `AdHocWriter.attribute()` at the end of the interface. Reserved names you must not use for custom attributes:
  `S`, `D`, `MinMax`, `A`, `V`, `X`, `ValueFor`, `Resumable`, `Keep*`, `Skip*`, the routing attributes, stream
  attributes. Attribute arguments must be compile-time constants; nested-struct constants referenced from an
  attribute must be `public`.
- **Branch pack scope**: `AdHocWriter.connectionAllPacks` uses `@<Project>` with `SkipName: @"Attribute$"`. When the
  source distinguishes wire-level messages from helper structs (SBE messages vs composites, DSDL messages vs
  nested types, Matter commands/events vs structs …), prefer an explicit list via `AdHocWriter.statePacks` so only
  the real messages become transmittable packs; helper types then stay sub-packs.
- **Request/response** in the source (ROS 2 `.srv`, DSDL services, Thrift/FlatBuffers services, Matter commands with
  a response) maps to the RPC shorthand inside the connection:
  `(L____________, ResponsePack) name(RequestPack req);` (Left calls, Right answers). Long-running flows
  (ROS 2 `.action`: goal → feedback… → result) map to an `interface X : Actor` with a linked state chain.
- **Never pin a source id into the Dashboard.** A pack id is AdHoc's own internal matter: the agent assigns and
  maintains it. Pass `null` for every pack and let the agent number them. The source's own identifier (CAN id, SBE
  template id, LwM2M object id, MSP command id, DSDL port id …) is *source metadata*: keep it as a
  `public const` inside the pack, or as a trailing comment on a field. The reference transformation,
  the Protobuf-to-AdHoc converter of this family, pins no id in the Dashboard either. A number that only places a
  field on the source's wire - a proto field number - is not an identifier and is not carried at all.
- **Collections**: `T[]` constant length `[D(N)]`, `T[,]` fixed-at-init, `T[,,]` list up to `[D(N)]`; `string` up
  to `[D(+N)]` chars; `Map<K,V>` / `Set<K>` with `[D(+N)]`. The global default is 255 items, which is wrong for
  almost every source: emit a **`_DefaultMaxLengthOf` enum** once per file with permissive values instead of
  capping every field or spraying `[D(N)]`, and use `[D]` only where the source states a real bound.
  ```csharp
  enum _DefaultMaxLengthOf { Arrays = 65_535, Maps = 65_535, Sets = 65_535, Strings = 65_535, }
  ```
- **Type aliases**: a class with a single field named `TYPEDEF` is an alias; use it for repeated constrained types.
- **Value packs** (fields totalling ≤ 8 bytes) need nothing special; the generator packs them itself.

## Convert the essence, not the syntax

The point of a converter is that someone who owns a specification in another system can run it through and
**immediately see their protocol expressed in AdHoc**. The result will not be perfect - AdHoc says far more than
the source format can - but it must be a usable starting point that is refined by hand, never one that has to be
rewritten from scratch. A literal transliteration fails that test: it produces valid AdHoc that uses none of
AdHoc's vocabulary, so the reader learns nothing about what AdHoc would do for them.

The reference for this is the Protobuf-to-AdHoc converter of this family. Read it
before writing an emitter. Five rules follow from it.

### 1. Carry over what the source knows about the *physics* of a number

This is AdHoc's headline capability and the thing no other schema language can express.

**The source's own wire format is irrelevant here.** AdHoc lays out its own frame, so "the source stores this
field fixed-width" is never a reason to decline `[A]` / `[V]` / `[X]` - a converter that argues that way has
confused the input encoding with the output one. What decides the attribute is the **physics of the field**: where
its values actually sit. In the words of the AdHoc README, *a temperature delta is small, a monotonic counter is
huge, a remaining-lease counter sits just under its ceiling - and the schema is the only place that can live.*

Sources state that physics more often than they look like they do: in units (`cdegC`, `mV`, `cm/s`, `degE7`), in
field names and descriptions, in declared ranges, in invalid markers, and in the encoding the source itself chose
when that choice was a statement about the data (proto `sint32` versus `fixed32` is such a statement).

| What the source tells you about the values | Emit | Meaning |
|:--|:--|:--|
| the author chose a **zigzag varint** (proto `sint32/64`, `int32/64`; Avro `int`/`long`; Thrift Compact `i32/i64`) | `[X]` | two-sided, clusters around zero |
| the author chose an **unsigned varint** (proto `uint32/64`) | `[A]` | one-sided, clusters at the low end |
| a **floor with no ceiling** - a counter, a sequence number, a length, ASN.1 `INTEGER (0..MAX)` | `[A(min)]` | clusters at `min`, rare excursions up |
| a value that **hugs its ceiling** - a remaining budget, a lease, headroom | `[V(max)]` | clusters at `max`, rare excursions down |
| a **delta, an offset, a rate, an error term** - anything centred on zero | `[X(amplitude)]` | two-sided, small either way |
| a **hard range** - ASN.1 `INTEGER (a..b)`, a DSDL `uintN`, a CAN signal width, an LwM2M range, a percentage | `[MinMax(a, b)]` | uniform in range, bit-packed |

**Check the arithmetic before emitting.** Varint wins only while the typical distance from the base stays under
about two million; beyond 268 435 455 it always loses. So a latitude scaled by 1e7, a Unix timestamp in seconds, a
monotonic uptime counter and a hash are all varint **losses** - not because the source stored them fixed-width, but
because their values are systematically large. A span narrower than one byte is rejected by the generator and
belongs in `[MinMax]` instead.

**Where the physics is the developer's call, say so at the field, not in the README.** Varint is a deliberate
decision taken after understanding the data, and a converter usually cannot take it. What a converter must not do
is drop the question silently. Leave a comment on the field naming the candidate and the reason, so the decision
is made where it belongs, with everything needed in front of the reader:

```csharp
// physics: airspeed error, centred on zero, typical |v| well under 1 000 → consider [X(2_000)]
short airspeed_error;
```

### 2. Map a concept to AdHoc's concept, not to a bag of metadata

A custom attribute is the right home for metadata AdHoc has no opinion about (a UI label, a unit string, a
source tag). It is the wrong home for something AdHoc models natively. In particular **time**:

| The source has | Emit | Not |
|:--|:--|:--|
| a wall-clock timestamp (FIX `UTCTIMESTAMP`, Matter `epoch-s`, Avro `timestamp-millis`, ASN.1 `GeneralizedTime`, LwM2M `Time`, ROS 2 `builtin_interfaces/Time`) | `DateTime` | `string` + `[SomeType("...")]` |
| a timestamp with a known epoch and resolution | a `class X : DateTimeDef { min; max; precision; }` alias | a raw integer |
| an elapsed duration (ROS 2 `builtin_interfaces/Duration`, Matter `elapsed-s`, Avro `time-millis`, a timeout) | a `class X : Duration { max; precision; }` alias | a raw integer + attribute |
| a cyclic "age" within a window | a `class X : TimeSpanDef { interval; precision; }` alias | a raw integer |
| "no argument" / an empty message (proto `Empty`) | one shared empty pack `class NoArg { }` | a pack with a dummy field |

Same idea elsewhere: a nullable wrapper becomes `T?`, a tagged union becomes a pack whose alternatives are all
optional, a request/response pair becomes the RPC shorthand, a one-way call becomes a non-transitional branch.

### 3. Keep source identity as metadata, never as protocol structure

See the id rule above. The same applies to field tags, wire offsets and encoding widths: they describe the
*source's* wire format, which AdHoc replaces with its own. Preserve them as `const` or comments so a migration
can be audited, and let AdHoc lay out the wire.

### 4. Leave a readable trail

Documentation text from the source becomes the pack's doc comment, and AdHoc pools it with the Dashboard
line, so `KeepDoc` / `SkipDoc` filters work on it. Anything the converter could not express must appear as a
comment at the place it was dropped, not only in the README, so the person refining the file sees it.

### 5. A hierarchy of names is a hierarchy of declarations

When the source names something by a path - a gRPC method `/package.Service/Method`, an HTTP operation
`GET /pets/{petId}`, a type `package.Message.Nested` - the description says it by *where the thing is declared*:
nested interfaces for the actors of a connection, nested packs and containers for the types, the namespace for
the package of the file itself. The path is not copied into an attribute and not folded into a name
(`google_rpc_Status`): the generated code is laid out by the declarations, and a string beside one lays out
nothing.

The opposite mistake is to nest by the words of the *format*. `components { schemas { … } }` and `paths { … }`
say nothing about the protocol, so they are not written.

## Validation is mandatory

```bash
./validate.sh AdHoc            # runs AdHocAgent with ADHOC_PARSE_ONLY=1 on a copy of every .cs
```

Every generated file must print `OK` (exit 0, no ERR/WRN). Iterate on the converter until it does. To see which
packs a branch collected, run the agent on a copy of the file with `ADHOC_DUMP_BRANCHES=1` as well: it writes
`branches.dump.txt` next to it. The agent's `INF … appears to be a flags enum` lines are informational and
acceptable.

## README of a project must contain

- purpose, and **links**: the format specification, the upstream repositories the samples come from, the parser or
  reference implementation of the format (all links verified to open);
- wherever a sample is named (tables, before/after, validation results), a link to its original page, the one
  `sources.txt` gives;
- the type / construct mapping table; what is dropped or approximated and why;
- fetch-samples, build, run and validate commands; the validation result for the shipped samples.
